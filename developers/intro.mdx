# Welcome to Pawtograder - Developer Guide

Pawtograder is a Next.js app on top of Supabase. Nearly everything a contributor needs to understand up front is about one thing: access control is enforced in Postgres, not in the application, so a feature is only as correct as its row-level security policies.

Start with [Local setup](/developers/local-setup) to get a stack running, then read the [access-control model](#access-control) below before you write a query.

| Layer | Technology |
|-------|------------|
| Framework | Next.js 15 App Router, React 18, TypeScript 5 |
| UI | Chakra UI v3 |
| Backend | Supabase: Postgres, Auth, Storage, Realtime, and Deno edge functions |

## Access control

### Row-level security

Access control lives in Postgres. Tables carry RLS policies that decide what each user can read and write based on their role in a class, and both the web app and the edge functions query as the signed-in user so those policies apply. Policies live in the migrations under `supabase/migrations/`, and most of their logic sits in SQL helpers such as `authorizeforclassinstructor` and `authorizeforclassgrader`.

Two consequences for anything you build:

- A missing policy fails closed and looks like a bug in your feature. If a query returns nothing, check the policy before the code.
- A privileged path is not privileged because the UI hides it. Anything reachable with a service-role client bypasses RLS entirely, which is why the [MCP server](/developers/mcp-server#authorization) confines its service-role use to the authentication layer.

### User roles

`user_roles.role` is an `app_role`, and that enum has four values (`utils/supabase/SupabaseTypes.d.ts:13949`, `:14155`):

| Role | Description |
|------|-------------|
| `student` | View course content, submit assignments, respond to surveys and polls |
| `grader` | Student permissions plus grading access in that class |
| `instructor` | Full management access to that class |
| `admin` | Platform-wide administration through the `app/admin/` dashboard: classes, GitHub organizations, LTI platforms and contexts, SIS sync, and notifications |

`student`, `grader`, and `instructor` are per class, so the same user can be an instructor in one course and a student in another. `admin` is not scoped that way in practice: the dashboard gate accepts any `admin` row for the user and ignores its `class_id` (`app/admin/layout.tsx:41-50`).

<Warning>
Several role gates ask whether a user holds a role in **any** class rather than in the class the request is about. The admin dashboard gate above is one; the MCP server's pre-tool check is another. When you add a gate, decide deliberately which of the two you mean, and rely on RLS for the per-class answer.
</Warning>

### Capabilities

On top of `app_role`, every class has a set of **class roles** (`class_roles` table) made up of capabilities. Each person in a class is linked to one class role through `user_roles.class_role_id`. The four default class roles mirror the four `app_role` values; instructors can also create custom grader roles.

Capabilities are stored in `role_capabilities` and checked through two SQL functions:

- `user_class_capabilities(user_id, class_id)` — returns the set of capabilities the user holds in that class, combining their class role's own capabilities with the default grader role's capabilities (for custom grader roles).
- `user_class_ids_with_capability(user_id, capability)` — returns the set of class IDs where the user holds a given capability. **Use this in RLS policies**, not an inline join, because an inline join only finds the user's own class role and misses the default grader role's capabilities.

The four capabilities and their default holders:

| Capability | Default holder |
|---|---|
| `manage_assignments` | instructor |
| `manage_review_assignments` | instructor |
| `publish_groups` | instructor |
| `manage_roles` | instructor |

When you add a new capability, add it to the `class_capability` enum, grant it to the instructor role in a migration, and write any new RLS policies using `user_class_ids_with_capability`. See `docs/capabilities.md` in the repository for the full policy rule and worked examples.

The `useCapability(capability)` React hook reads `user_class_capabilities()` on the client and re-fetches when the viewer's role or any role's capabilities change (via the staff Realtime channel). Use it to show or hide UI controls; the database policy is the authoritative gate.

### Profiles

Every enrollment carries two rows in `profiles`, and `user_roles` points at both through `private_profile_id` and `public_profile_id` (`hooks/useClassProfiles.tsx:24-25`). Both columns are unique, so each profile belongs to exactly one enrollment, which is why several foreign keys reference `user_roles(private_profile_id)` rather than `profiles(id)`.

| | Private profile | Public profile |
|---|---|---|
| `is_private_profile` | `true` | `false` |
| `name` | The user's real or preferred name | A generated `adjective-noun-number` pseudonym |
| `avatar_url` | Their real avatar | A DiceBear identicon seeded from the pseudonym |

Both are created together at enrollment (`supabase/functions/_shared/EnrollmentUtils.ts:152-158` and `:176-183`). Only the private profile's name is user-editable, as the **preferred name** in the user menu (`app/course/[course_id]/UserMenu.tsx:425-438`).

Which profile a row references is what decides whether the record is attributable, so pick deliberately when you add a column:

- **Always private.** Submissions (`supabase/migrations/20250330003141_remote_schema.sql:2412-2413`), gradebook rows (`supabase/migrations/20250614231720_gradebook.sql:197`), and help requests.
- **Chosen per post.** A discussion thread or chat message stores the public profile when the author opts into anonymity and the private profile otherwise (`app/course/[course_id]/discussion/new/page.tsx:97`, `components/ui/message-input.tsx:129`). Reads therefore have to match against both ids. Graders' rubric and line comments switch to the public profile when the assignment has `grader_pseudonymous_mode` on (`hooks/useAssignment.tsx:73-76`).
- **Always public.** Poll responses (`app/poll/[course_id]/page.tsx:82-98`).

`is_private_profile` also serves as a discriminator for "one row per enrolled person" when you need a roster without joining `user_roles` (`hooks/useCourseController.tsx:133`).

<Warning>
`create_class_with_admin` gives the creating admin their real name on **both** profiles rather than generating a pseudonym (`supabase/migrations/20250820185937_admin_portal_system.sql:81-100`). Do not treat a public profile name as guaranteed to be anonymous.
</Warning>

## Data access

Prefer a Postgres RPC over a Next.js server action or an edge function for data operations. Edge functions are for integrations that need an external API, such as GitHub, Discord, or AWS Chime, not for general data access.

Components do not query Supabase directly. `TableController` (`lib/TableController.ts`) caches and loads data scoped to a context such as a course, assignment, submission, or discussion thread, and the realtime controllers in `lib/` extend it for live updates. Components consume all of it through the hooks in `hooks/`.

`utils/supabase/SupabaseTypes.d.ts` is generated and copied into `supabase/functions/_shared/`. Regenerate it with `npm run client-local` after a schema change; do not hand-edit it.

## OAuth server (OIDC provider)

Pawtograder can act as an OAuth 2.1 / OIDC identity provider, so tools like
Forgejo and Coder can offer "Sign in with Pawtograder". This is enabled through
Supabase Auth's OAuth server support.

### Enabling the OAuth server

In `supabase/config.toml`, set:

```toml
[auth.oauth_server]
enabled = true
consent_path = "/oauth/consent"
```

The consent page at `app/(auth-pages)/oauth/consent` shows the requesting
application and its requested scopes, records the user's Approve or Deny
decision, and forwards back to the application. When GoTrue already has the
user's consent for that application, it forwards immediately without showing
the page again.

### Registering OAuth clients

Register Forgejo and Coder as OAuth clients through the Supabase Auth admin
API (GoTrue's `POST /admin/oauth/clients`). The chart's bootstrap scripts
handle this automatically when `forgejo.enabled` or `coder.enabled` is set in
the Helm values.

### Scopes

The OAuth server exposes the `openid`, `profile`, and `email` scopes. The
`profile` scope provides the user's name (which is their email address) and
the `email` scope provides their email address.

### Redirect validation

The OAuth server validates redirect URIs strictly. Each client's allowed
redirect URIs must be registered at client-creation time; unregistered URIs
are rejected before any user interaction. The `GOTRUE_URI_ALLOW_LIST` must
include each web channel host with `/**` (not just `/*`, which stops at one
path segment).

### Sign-in flow

1. The user clicks "Sign in with Pawtograder" in Forgejo or Coder.
2. Forgejo/Coder redirects to Pawtograder's authorization endpoint with a
   PKCE challenge.
3. If the user is not signed in, they are sent to the sign-in page with the
   OAuth return path preserved through the `redirect` query parameter.
4. After sign-in (or if already signed in), the consent page is shown (or
   skipped if consent was already given).
5. Pawtograder redirects back to Forgejo/Coder with an authorization code.
6. Forgejo/Coder exchanges the code for tokens and signs the user in.

<Note>
GoTrue requires PKCE on every authorization request. Forgejo skips PKCE on
the first sign-in after a login source is added through the CLI, so the
bootstrap scripts spend one request to satisfy this requirement.
</Note>

## Contributing

1. Fork the repository and create a feature branch.
2. Make your changes. Regenerate types with `npm run client-local` if you touched the schema.
3. Run `npm run format` before committing. CI rejects unformatted code (`AGENTS.md:42`).
4. Run the checks CI runs: `npm run lint`, `charts/pawtograder/tests/render-guardrails.sh`, and `npm run test:functions` (`lint.yml:33`, `:47`, `:60`).
5. Run the tests your change affects: `npm test` for Jest, `npx playwright test` for end-to-end.
6. Open a pull request.

<Note>
No workflow runs a standalone TypeScript typecheck, and the full Jest suite is not part of CI. See [Continuous integration](/developers/local-setup#continuous-integration) for what each workflow actually runs.
</Note>
